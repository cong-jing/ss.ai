# Persona-flow 长期记忆保存机制需求文档

## 1. 背景

Persona-flow 的目标不是做一个普通的问答机器人，而是构建一个能够持续对话、保持角色一致性，并在长期互动中逐渐积累理解的角色对话系统。

在聊天陪伴、NPC 行为控制、角色关系变化、任务状态推进等场景中，系统不能只依赖当前上下文。用户曾经表达过的偏好、经历、状态、目标、关系变化、世界设定，以及角色自身的长期设定，都可能影响后续回复和行为决策。

因此，系统需要具备长期记忆保存能力。

这里的“记忆”不是简单保存聊天记录，也不是把每一句话都复制到数据库，而是从对话中提取未来可能有用的信息，将其整理为稳定、可复用、可检索、可更新的长期记忆。

## 2. 目标

本阶段的目标是实现 Persona-flow 的记忆写入机制。

具体来说，系统需要能够在每轮对话后判断：

1. 本轮对话中是否出现了值得长期保存的信息。
2. 该信息是全新的记忆，还是已有记忆的重复、补充、修正或冲突。
3. 如果需要保存，应以怎样的形式写入数据库。
4. 如果不需要保存，应避免重复写入和无意义积累。

最终目标是让系统逐渐形成可维护的长期记忆，而不是把 memory 数据库变成另一份聊天日志。

## 3. 为什么需要长期记忆

普通 LLM 对话主要依赖当前上下文窗口。当上下文变长或会话结束后，模型无法自然保留过去的信息。

对于普通企业 FAQ 或文档问答来说，这个问题可以通过文档检索解决。但 Persona-flow 面向的是更复杂的互动场景：

用户可能在长期对话中逐渐透露自己的偏好、习惯、生活状态和目标。

角色可能需要记住自己和用户之间的关系变化。

NPC 可能需要基于过去事件改变行为。

用户可能会给角色添加新的设定。

任务、剧情、世界状态可能随着对话推进而改变。

这些信息如果只存在于聊天记录中，后续很难稳定使用。系统需要把它们提取成更高层次的长期记忆。

## 4. 记忆不应等同于聊天记录

本系统中的记忆不是原始消息。

原始消息是用户和角色在某一时刻说过的话，可能包含口语、情绪、调侃、上下文省略和临时表达。

长期记忆应该是经过整理后的稳定信息。

例如，用户说：

“我最近晚上不太敢喝咖啡了，喝了睡不着，烦死。”

这句话本身不适合原封不动作为长期记忆。更合适的记忆是：

“用户最近避免在晚上喝咖啡，因为会影响睡眠。”

这样保存后，系统在未来给用户建议、生成陪伴式回应，或判断用户状态时，都能更稳定地使用这条信息。

## 5. 记忆保存的基本原则

记忆保存应遵循以下原则：

第一，只保存未来可能有用的信息。

寒暄、临时情绪、一次性琐事、重复表达，不应该轻易进入长期记忆。

第二，记忆应尽量稳定、简洁、可理解。

系统应避免保存过于口语化、带角色调侃语气、含混不清或无法独立理解的内容。

第三，记忆应保留来源。

每条记忆最好能追溯到相关消息，以便调试、解释和后续修正。

第四，记忆应允许更新和归档。

用户的偏好、状态、目标、关系和设定可能会变化。系统不能只会追加，还需要支持更新旧记忆、合并补充信息，或归档已经失效的记忆。

第五，记忆写入不能完全信任主模型。

LLM 可以提出“这条信息可能值得记”，但最终是否写入数据库，需要经过系统层面的提交判断。

## 6. 总体实现策略

本阶段采用“候选记忆生成 + 提交判断”的两阶段策略。

第一阶段，由主模型在对话结构化输出中提出 memory write candidate，也就是候选记忆。

候选记忆表示模型认为本轮对话中可能存在值得保存的信息。但它只是草稿，不代表一定会进入数据库。

第二阶段，系统对候选记忆进行提交判断。

系统需要检查这条候选记忆与已有记忆之间的关系。它可能是：

全新记忆，需要创建。

已有记忆的重复，不需要新增。

已有记忆的补充，需要合并或更新。

已有记忆的修正，需要覆盖旧内容。

与旧记忆冲突，需要归档旧记忆并保存新记忆。

价值过低或不适合长期保存，需要忽略。

这个提交判断过程可以由规则、相似记忆检索和独立的 memory judge 共同完成。

## 7. 为什么不直接保存主模型输出

主模型正在承担角色回复任务。它需要考虑角色语气、情绪表现、对话自然度和当前场景。

这会导致它在判断记忆时可能出现以下问题：

它可能把角色的主观语气写进记忆。

它可能重复保存已经存在的信息。

它可能把一次性事件误判成长期记忆。

它可能为了配合回复，生成听起来合理但不够稳定的记忆。

它可能忽略记忆与旧记忆之间的冲突。

因此，主模型适合提出候选记忆，但不适合直接决定数据库写入。

数据库提交应由更冷静、更保守的系统流程来控制。

## 8. 为什么需要相似记忆检索

重复记忆不会总是以完全相同的文字出现。

例如以下几句话语义接近：

“用户喜欢咖啡。”

“用户偏好咖啡。”

“用户经常喝咖啡。”

“用户对咖啡有明显偏好。”

如果只做字符串比较，系统无法判断它们是否重复。

因此，在候选记忆提交前，系统需要检索已有的相近记忆。检索到相近记忆后，再判断新候选是重复、补充、修正还是冲突。

这个检索可以先从简单策略开始，例如根据记忆类型、相关实体、标签、时间范围缩小候选，再使用语义相似度寻找接近的旧记忆。

本阶段不要求一开始就接入完整向量数据库。对于小规模 demo，可以先使用轻量的相似度检索方式。重点是建立“提交前检查旧记忆”的流程，而不是追求复杂基础设施。

## 9. 为什么可能需要 memory judge

相似度只能告诉系统“两条记忆可能相关”，但不能可靠判断它们的真实关系。

例如：

“用户喜欢咖啡。”

“用户现在不喝咖啡，因为会影响睡眠。”

这两条记忆在语义上很接近，都和咖啡有关。但它们不是重复，而是状态变化或偏好修正。

因此，在相似记忆检索之后，系统可能需要一个独立的 memory judge 来判断：

候选记忆是否真的值得保存。

它是否和旧记忆重复。

它是否提供了新细节。

它是否修正了旧记忆。

它是否与旧记忆冲突。

最终应该创建、更新、合并、忽略还是归档。

memory judge 的职责不是角色扮演，而是做保守的记忆提交决策。

## 10. 记忆主体应以自然语言为主

系统不应试图把所有记忆都拆成固定数据库字段。

现实中的记忆非常复杂，包括用户住在哪里、用户上周参加了什么活动、用户正在做什么项目、用户给角色添加了什么设定、角色对用户的关系变化、NPC 对玩家的态度、世界状态的改变等。

这些信息很难全部用固定的 subject / predicate / object 结构表达。

因此，本系统应以自然语言记忆作为主体。

结构化信息只作为辅助索引，例如：

记忆范围：用户、角色、当前会话、世界。

记忆类型：事实、偏好、事件、关系、任务状态、设定、指令、摘要。

相关实体：用户、角色、地点、物品、任务、公司、项目等。

标签：用于粗略分类和检索。

时间信息：用于表示事件发生时间或记忆有效期。

这些辅助字段用于帮助检索、去重和管理生命周期，而不是完整表达世界。

## 11. MVP 范围

本阶段优先实现记忆写入侧的最小闭环。

MVP 应包括：

主模型能够输出候选记忆。

系统能够把候选记忆记录下来。

系统能够初步判断是否创建新记忆。

系统能够避免最明显的重复写入。

系统能够记录候选记忆、提交判断和最终写入结果，方便调试。

暂时不要求完整实现复杂更新、冲突处理、向量数据库、agent loop 或高精度记忆检索。

但系统设计上应保留后续扩展空间。

## 12. 非目标

本阶段不追求以下内容：

不追求把所有对话都记下来。

不追求建立完整知识图谱。

不追求一次性解决所有记忆冲突。

不追求立刻实现生产级向量数据库。

不追求让主模型直接管理所有记忆。

不追求复杂 agent loop。

本阶段重点是建立正确的记忆写入思想和提交流程。

## 13. 预期效果

完成本阶段后，Persona-flow 应具备以下能力：

系统能够从对话中提取可能有长期价值的信息。

系统能够把口语化表达整理为稳定记忆。

系统不会盲目把所有候选记忆直接写入数据库。

系统能够初步避免重复记忆。

系统能够为后续的记忆检索、角色一致性、NPC 行为控制和长期关系建模打基础。

对于 demo 展示来说，这可以说明项目不是简单套壳聊天，而是在构建一个可维护的长期记忆系统。

## 14. 后续扩展方向

在完成 MVP 后，可以继续扩展以下能力：

引入更稳定的相似记忆检索。

加入独立 memory judge。

支持记忆更新、合并、归档和冲突处理。

加入记忆读取请求日志。

实现基于 memory read request 的检索流程。

将检索结果注入主回复流程。

进一步支持角色设定、任务状态、世界状态和 NPC 行为决策。

最终，Persona-flow 的记忆系统应从“保存用户信息”扩展为“维护角色、用户、关系、任务和世界状态的长期上下文系统”。

## 15. 总结

本阶段要实现的不是一个简单的 memory insert 功能，而是一个受控的记忆保存流程。

LLM 可以提出候选记忆，但系统需要判断这条候选是否真的值得进入长期记忆。

长期记忆应当是经过整理、可追溯、可更新、可去重的信息，而不是聊天记录的复制。

这个机制的核心价值在于，让 Persona-flow 的角色不只是当前上下文中的表演者，而是能够在长期互动中逐渐积累理解、保持一致性，并据此影响后续回复和行为。
